# ロードマップ(参考情報・現バージョンでは実装しない)

将来の拡張計画と、それが手前のバージョンの設計に課す制約をまとめた文書。
ここにある機能を先取りで実装しないこと([requirements.md](requirements.md) §2.2)。

**v0.2 / v0.3 は初期仕様書由来の計画。v0.4 以降の切り方と順序は Claude Code による提案**で、
入れ替え・統合は自由。いずれも着手前にスコープをユーザーと確認し、確定した内容を
requirements.md に昇格させてから実装に入ること。

## 全体像

| ver | テーマ | 主な価値 |
|---|---|---|
| v0.1 | 単発実行の完成(開発中) | 依頼 → リアルタイム把握 → 成果物受領が 1 本通る |
| v0.2 | エージェント定義の管理と共有 | チーム全員が同じ定義で同じ結果を得られる |
| v0.3 | アプリ本体の更新 | チーム配布後の維持コストを下げる |
| v0.4(提案) | 定期実行と通知 | 定型業務の自動化 — このアプリの本来価値の核心 |
| v0.5(提案) | 並行実行とダッシュボード | 複数業務の同時進行と俯瞰 |
| v0.6(提案) | 監査とガバナンス | 非エンジニアを含むチーム運用の安全担保 |
| v1.0 | 安定版 | 開発者が同席しなくてもチームで回る状態 |

## v0.2: エージェント定義の管理と共有

### 内容

- 定義の作成・編集 UI(frontmatter のフォーム化)
- 定義リポジトリからの同期(GitHub API で zip を取得して展開)
- **共有スコープ(読み取り専用)と個人スコープ(編集可)の分離**
  - 共有スコープのエージェントは編集不可、「複製して編集」で個人スコープへ
  - Copilot CLI 側のスコープ階層(リポジトリ / ユーザー / 組織 / エンタープライズ)に対応させる
- 同期した定義のバージョン(コミットハッシュ)を UI と成果物に記録

### 設計上の論点

- 同期先は CLI の規約パス(`~/.copilot/agents/` 等)か、アプリ管理のフォルダか。
  CLI 規約パスに書くと CLI 単体利用と共存できるが、他ツールとの競合に注意
- 「複製して編集」時の名前衝突(CLI はユーザー > リポジトリ > 組織の優先順で解決する)

### 未決事項

- 定義リポジトリの場所(組織リポジトリか、専用リポジトリか)と認証方式

## v0.3: アプリ本体の更新

### 内容

- 起動時に最新版の有無を確認し、**通知のみ**行う(自動適用しない)
- 通知には版数と変更点の要約を出し、入手方法を案内する
- **どの方式でも、ダウンロードしたファイルのハッシュ検証(SHA-256)は必須**

### 配布元の選択肢(未決)

| 方式 | 利点 | 問題 |
|---|---|---|
| GitHub Releases(public) | 実装が素直(Releases API) | 社内アプリを public にできるか |
| GitHub Releases(private) | アクセス制御を GitHub に委ねられる | **PAT の配布問題が未解決**(各人の fine-grained PAT を設定させるか) |
| 社内共有フォルダ | 認証不要(AD 任せ)、実装最小 | 版管理が手運用になる。ハッシュ・版数のマニフェストファイルを置いて補う |

### 段階案

1. **v0.3.0**: 更新の検知と通知のみ。適用はユーザーが手動でコピー
2. **v0.3.x(運用が安定してから)**: 半自動適用 — 新 exe をダウンロード・検証し、
   実行中 exe をリネーム(Windows は実行中でもリネーム可)→ 新 exe を配置 → 再起動を促す
   ポータブル配布(単体 exe)と矛盾しない方式であること

### 未決事項

- 配布元(上表)。private リポジトリ案の認証方式
- 確認頻度(起動時のみ/日次)

## v0.4(提案): 定期実行と通知

アンケート集計も予算分析も月次・四半期の繰り返し業務であり、
「毎月 1 日に自動で回って、朝には成果物ができている」が本来のゴール。
初期仕様書の「定期実行(スケジューラ)」を具体化したもの。

### 内容

- スケジュール定義(`data/schedules.json`): エージェント・プロンプトテンプレート・cron 相当の周期
- 実行キュー: 発火が重なっても直列に消化(同時実行数は当時の上限に従う)
- 完了・失敗の Windows トースト通知(手動実行にも適用)
- 履歴に起動種別を記録(`trigger: "manual" | "scheduled"`)

### 設計上の論点(重要)

- **無人実行と承認ダイアログは両立しない。** スケジュール実行には「事前承認プロファイル」を必須とし、
  自動承認できない権限要求が出たら**即座に失敗として記録**する(ダイアログを出して朝まで待たない)。
  権限判定 `permissions::decide` が UI 非依存の純関数であることが効いてくる(v0.1 で担保済み)
- スケジューラの持ち方: アプリ常駐(タスクトレイ)か、Windows タスクスケジューラ +
  ヘッドレス起動モード(`agent-deck.exe --run-schedule <id>`)か。
  ポータブル配布との相性はタスクスケジューラ登録の方が悪い(パス移動で壊れる)ため、
  常駐案を第一候補とする
- 失敗時の再試行はしない(定型業務は「失敗を通知して人が見る」で十分。再試行は誤発火のリスクの方が大きい)

### 未決事項

- 常駐(タスクトレイ)を許容するか
- プロンプトテンプレートの変数(実行日付など)の記法

## v0.5(提案): 並行実行とダッシュボード

### 内容

- 複数セッションの同時実行(上限は設定値。[open-questions.md](open-questions.md) #4 の解決が前提)
- 実行ビューのタブ化またはセッション切り替え
- 全セッションを俯瞰するダッシュボード(進行状況・待機中の承認要求・直近の失敗)
- 同一 `outputDir` への同時書き込みの検出と警告(成果物の混線防止)

### 設計上の論点

- `AppEvent` は全イベントに `session_id` を含むため、イベント設計は変更不要(v0.1 で担保済み)。
  変更が要るのはセッション管理(1 本前提の AppState)と UI
- Copilot 側のレート・クレジット消費が並行数に比例する。上限の既定値は小さく(2〜3)始める

## v0.6(提案): 監査とガバナンス

二次利用者(非エンジニア)の利用が定着した段階で、「誰が・いつ・何を・どのデータで」を
説明できる状態にする。初期仕様書の「hooks による監査ログの併用」を具体化したもの。

### 内容

- 監査ログ: 全ツール実行・権限判定の結果を追記専用ログに記録
  (SDK/CLI の hooks 機構が使えるか要裏取り。使えなければ PermissionHandler と
  イベント購読で全量記録する)
- 成果物の来歴(provenance): どの入力ファイル・定義バージョン・モデル・プロンプトから
  生成されたかを成果物と紐づけて保存(architecture.md §8.2 のフッター記録の拡張)
- 設定のロック: 管理者が配布する `deniedTools` をユーザーが緩められないようにする
- ログの保持期間と世代管理([open-questions.md](open-questions.md) #5 の解決)

### 未決事項

- 監査ログの置き場(ローカルのみか、共有フォルダへ複製か)
- 「管理者」の概念を持ち込むか(ポータブルアプリとの相性)

## 継続タスク: Copilot 本体との重複チェック

新機能を足す前・四半期ごとに、その機能が Copilot CLI / VS Code 本体に取り込まれていないかを
確認すること([positioning.md](positioning.md) の見直し方針)。吸収された自前実装は捨てて委ねる。

## v1.0: 安定版の条件

機能ではなく状態で定義する。以下がすべて成り立ったら v1.0 とする。

1. 二次利用者が、開発者の同席なしで日常業務に使えている
2. 定義の共有(v0.2)とアプリの更新(v0.3)が運用として回っている
3. 主要な失敗モード(CLI 未認証・ポリシー無効・出力先書き込み不可・タスク失敗)が
   すべて UI 上で自己説明的(利用者がエラーメッセージだけで対処できる)
4. 利用者向けガイド(開発者向けではない操作説明書)が存在する
