## v1.1(提案): 文章を書かせない(依頼も定義も)

**解く問題**: 成果物の質が「利用者が書いた文章」に依存している。
依頼のプロンプトも、エージェント定義の Instructions も、白紙から日本語で書くのは難しい。
二次利用者(非エンジニア)にとって最大の壁はここで、v1.0 の状態条件 1
「開発者の同席なしで使えている」が満たせるかどうかを実質的に左右する。

### 内容 (a) 依頼フォーム

- エージェント定義に入力項目(項目名・種別・既定値・必須か)を持たせ、
  利用者は値を埋めるだけにする。プロンプトはテンプレートから生成する
- テンプレート変数(実行日・対象期間・選択した入力ファイル名など)。
  v0.4 で先送りにした「プロンプトテンプレートの変数記法」をここで確定させる
- 定期実行(v0.4)と手動実行で**同じテンプレートを共有**する。
  片方だけ育つと「スケジュールでは正しく動くのに手動では違う結果」が起きる

### 内容 (b) エージェント作成を Copilot に支援させる

定義を書けるのが開発者だけだと、業務が増えるたびに開発者がボトルネックになる。
**定義の下書きは Copilot 自身に書かせる**(実行エンジンを既に持っているので追加コストは小さい)。

- 「アンケート結果を集計してレポートを作りたい」程度の説明から、
  name / description / tools / model / Instructions 本文の**下書き**を生成し、
  定義エディタに流し込む。**保存は人がレビューしてから**
- 既存定義の改善にも同じ導線を使う。失敗した実行の履歴・エラーを渡して直させる
  (v1.4 の「失敗 → 定義修正」の導線と接続する)
- 生成時のメタプロンプトに**このプロジェクトの方針を埋め込む**。
  特に [architecture.md](architecture.md) §8.1(数値集計はスクリプトにやらせる)と
  §8.2(成果物フッターに定義バージョンとモデルを記録)、および
  「ファイル出力は write ツールを使う」(シェル書き込みは自動承認の対象外)。
  ここを外すと、生成された定義が最初から誤った数字を出す作りになる

### 設計上の論点

- フォーム定義の置き場: `.agent.md` frontmatter の独自キーか、agents.json 側か。
  frontmatter に置けば共有フォルダ同期でそのまま配れる(CLI 単体では未知キーとして無視される)が、
  **現在の `render_agent_md` は未知 frontmatter キーを保存時に落とす**ため先に直す必要がある
  (下の「塞いではいけない点」参照)
- 変数の未入力・空値の扱い。無人実行では欠損を即失敗にする(v0.4 の方針と揃える)
- **生成された `tools` を鵜呑みにしない。** 定義のツール欄はガードレールそのものであり、
  LLM に「必要そうなツール」を書かせると広がる方向に倒れる。生成結果は最小に丸め、
  広げるのは人の明示操作にする(非目標「承認を減らす方向の便利化をしない」と同じ理由)
- 定義生成セッション自体には**ツールを一切与えない**(テキスト生成のみ)。
  ファイル書き込みは agent-deck 側が行うので、既存の権限モデルの外に出ない
- `description` は Copilot の自動委任判断に使われる。生成文がここに効くことを
  メタプロンプト側で意識させる(サブエージェントとして呼ばれる定義かどうかで書き方が変わる)
- 共有スコープの定義は読み取り専用なので対象外(「複製して編集」の後に使う)
- **Copilot CLI / VS Code 側に同等の定義作成支援が既にあるか要裏取り**(`doc-researcher`)。
  あれば自前実装せずそちらへ委ねる([positioning.md](positioning.md) の見直し方針)

### 未決事項

- フォーム定義の置き場と変数記法([open-questions.md](open-questions.md) #9)

## v1.2(提案): 成果物を信じられる状態にする

**解く問題**: v0.6 の来歴は「誰が・いつ・どの定義で作ったか」に答えるが、
**「その数字は合っているか」には答えない**。業務データを扱うアプリとしてはここが最後の障壁で、
一度でも誤った数字を配ると運用そのものが止まる。

### 内容

- **集計スクリプトの保存をアプリ側で担保**する。[architecture.md](architecture.md) §8.1 の
  「数値集計はスクリプトにやらせる」は現状エージェント定義の Instructions 頼みで、
  守られたかどうかを検証していない。出力にスクリプトが無い実行は成果物に注記を出す
- **再現実行**: 同じ入力・同じ定義で再実行し、**数値の差分だけ**を提示する。
  ぶれたら利用者が気づける(文章は LLM の非決定性で必ず変わるので比較対象にしない)
- 成果物と根拠(読んだ入力ファイル・実行したスクリプト)の紐づけ表示。
  `provenance.inputFiles` は v0.6 で取得済みなので、集めるより見せる作業が主
- 定義テンプレートに自己検証ステップ(合計が元データと一致するか等)を標準装備する

### 設計上の論点

- 再現実行はトークンを倍消費する。全実行に自動で付けず、利用者が任意に叩く形にする
- 「差分あり」をどう見せるか。警告にすると狼少年になり、出さないと意味がない。
  数値セルの一致率など、閾値で切れる指標に落とす必要がある

## v1.3(提案): データの入口を広げる(MCP)

**解く問題**: 入力データを人が手で入力フォルダに置く運用が残っている。
実業務のデータは共有ドライブ・基幹システム・SaaS の中にある。

### 内容

- 定義の `mcp-servers`(CLI/SDK 側は対応済み — [sdk-notes.md](sdk-notes.md))を
  agent-deck の定義エディタから設定できるようにする
- MCP ツールを自動承認・拒否リストの対象として扱う(`server/tool` 記法)。
  権限判定の経路自体は既にある(`PermissionRequestKind::Mcp` は tool_name 付きで
  `decide` を通り、既定では Ask に落ちる)
- 前提の修正: `render_agent_md` が未知 frontmatter キーを落とすため、
  定義エディタで保存すると `mcp-servers` が消える。**先にここを直す**

### 設計上の論点

- **ガードレールの範囲が広がる。** MCP 経由の書き込み・送信は outputDir 判定の外側にあり、
  「出力フォルダの中だけ自動承認」という v0.1 からの中核ポリシーが覆えない領域が増える。
  既定は全 Ask、自動承認はサーバー単位で明示的に足させる形を崩さないこと
- 接続情報(社内システムの認証)をどこに置くか。
  [requirements.md](requirements.md) §2.3「認証情報を保存しない」方針との整合が必要で、
  MCP サーバー側の設定に委ねる(agent-deck は参照するだけ)のが第一候補

### 未決事項

- MCP の利用を許容するか、するとして接続情報の扱い([open-questions.md](open-questions.md) #10)

## v1.4(提案): 運用の見える化(コストと実績)

**解く問題**: 「この運用を続けてよいか」を判断する材料が無い。
実行ごとのトークンは記録済みだが、月単位・エージェント単位で集計されていない。

### 内容

- エージェント別・月別の実行回数 / 成功率 / トークン量の集計ビュー
  (history.jsonl から算出でき、**新しいデータ収集は要らない**)
- 月間トークンの閾値超過を通知
- 失敗の傾向表示と、そこから定義編集への導線(「失敗した実行 → この定義を直す」)

### 設計上の論点

- 課金単位(クレジット)を SDK から取得できるかは未確認。取れなければトークン数を代理指標とし、
  **金額と誤解されない表記**にする(要裏取り: `doc-researcher`)

## v2.0 の論点(まだ決めない)

- **エンジンの抽象化**: Copilot 以外の実行エンジンを選べるようにするか。
  SDK 依存は `copilot.rs` にほぼ閉じているので技術的な障壁は低いが、
  「AI エンジンを持たない・Copilot の賢さをそのまま使う」という
  [positioning.md](positioning.md) の前提を薄める。価値が具体化するまで着手しない
- **複数 PC・サーバー実行**: 常駐の先にある話。ポータブル配布との相性が悪い
- **撤退**: Copilot 本体が器の部分を吸収したら、対応する自前実装を**削除する**。
  機能を足すことだけが進化ではない(下記「継続タスク」)

## 非目標(足さないと決めておくこと)

膨張を防ぐための線引き。ここを越える要望が来たら、まず [positioning.md](positioning.md) に
立ち返って「素の Copilot / VS Code でやるべきでは?」を確認する。

- **汎用チャットアプリにしない。** 対話は「定型業務の遂行に必要な範囲」(質問への回答・
  継続依頼)まで。雑談・調べ物の窓口は素の Copilot の領分
- **コード生成 IDE にしない。** 主用途は業務ドキュメントの生成([requirements.md](requirements.md) §1.1)
- **独自の AI エンジンを持たない。** モデル呼び出しは Copilot SDK 経由のみ
- **承認を減らす方向の便利化をしない。** 自動承認は常に「範囲を明示して足す」形でだけ増やす。
  「面倒だから全部許可」を1クリックで作れる UI は用意しない

## 継続タスク: Copilot 本体との重複チェック

新機能を足す前・四半期ごとに、その機能が Copilot CLI / VS Code 本体に取り込まれていないかを
確認すること([positioning.md](positioning.md) の見直し方針)。吸収された自前実装は捨てて委ねる。

確認は `doc-researcher` エージェントで行い、結果を positioning.md と
[sdk-notes.md](sdk-notes.md) に反映する。特に監視すべき領域:

- フォルダ単位の書き込み承認ポリシー(→ 固有価値 1 が消える)
- 実行履歴・監査ログの標準 UI(→ 固有価値 3)
- 定義の GUI 編集と非エンジニア向けクライアント(→ 固有価値 2)

## v1.0: 安定版の条件

機能ではなく状態で定義する。以下がすべて成り立ったら v1.0 とする。

1. 二次利用者が、開発者の同席なしで日常業務に使えている
2. 定義の共有(v0.2)とアプリの更新(v0.3)が運用として回っている
3. 主要な失敗モード(CLI 未認証・ポリシー無効・出力先書き込み不可・タスク失敗)が
   すべて UI 上で自己説明的(利用者がエラーメッセージだけで対処できる)
4. 利用者向けガイド(開発者向けではない操作説明書)が存在する

進捗は [development.md](development.md) §4 のマイルストーン欄を参照。
