### 0.1 最初にやること

本仕様書のコードを書き始める前に、以下を必ず確認してください。GitHub Copilot 関連は

2. `github/copilot-sdk` リポジトリの `rust/README.md` と `examples/` を読む
3. Copilot CLI のカスタムエージェント（`.agent.md`）の配置パスと

4. Tauri v2 の現行バージョンと、使用するプラグインの対応状況を確認する

確認の結果、本仕様書の記述と食い違う点があれば、**実装を進める前に指摘してください。**

- **可読性と監査性を最優先。** 動けばよいコードではなく、後から人が読んで追える構造にする

- コメントと識別子は日本語可。ただしコード上の識別子は英語で統一する

## 1. プロジェクト概要

### 1.1 目的

役割を定義した AI エージェントに定型業務を依頼し、その稼働状況をリアルタイムに把握し、
成果物ファイルを受け取るための Windows デスクトップアプリケーション。

### 1.2 想定する業務

コード生成ではなく、**業務ドキュメントの生成**が主用途。

- アンケート結果の集計と分析レポートの作成
- 予算消費状況の分析レポートの作成
- その他、入力データ → 分析 → レポート出力の形をとる定型業務

### 1.3 利用者

- 一次利用者: 開発者本人
- 二次利用者: 同一チームのメンバー（数名）。エンジニアとは限らない

### 1.4 名称

**`agent-deck` に決定**(2026-08-12。当初の仮称は `agent-console`)。

## 2. 技術スタック

| 区分 | 選定 | 状態 |
|---|---|---|
| デスクトップフレームワーク | Tauri v2 | 決定 |
| バックエンド | Rust | 決定 |
| Copilot 連携 | `github-copilot-sdk`（公式 Rust SDK） | 決定 |
| フロントエンド | React + TypeScript + Vite | 推奨（変更可） |
| 状態管理 | 標準の useState / useReducer で足りる範囲に収める | 推奨 |
| 配布形態 | インストーラーなしのポータブル exe | 決定 |

### 2.1 クレート選定の注意

crates.io には Copilot CLI を制御する非公式クレートが複数存在します
（`copilot-sdk-supercharged`、`copilot-client` など）。
**採用するのは `github/copilot-sdk` リポジトリ由来の `github-copilot-sdk` のみ**とします。

### 2.2 CLI の同梱

`github-copilot-sdk` は既定の `bundled-cli` フィーチャーで Copilot CLI バイナリを
実行ファイルに埋め込みます。

- **v0.1 では `default-features = false` にして無効化する**（ビルド時間とバイナリサイズを優先）
- ローカルの CLI を `COPILOT_CLI_PATH` または設定から解決する
- チーム配布を始める段階で、同梱の有効化を再検討する

なお SDK と CLI はバージョンが対で管理されています。バージョンは固定し、
更新時は必ず動作確認をセットで行ってください。

## 4. アーキテクチャ

### 4.1 責務の分割

```
┌─────────────────────────────────────────┐
│ フロントエンド (React / TypeScript)      │
│  - 画面描画、ユーザー操作                 │
│  - invoke でコマンド呼び出し              │
│  - listen でイベント受信                  │
└──────────────┬──────────────────────────┘
               │ Tauri IPC
┌──────────────┴──────────────────────────┐
│ バックエンド (Rust)                       │
│  - Copilot SDK のセッション管理           │
│  - イベント購読 → フロントへ emit         │
│  - 設定ファイルの読み書き                 │
│  - 権限判定                               │
└──────────────┬──────────────────────────┘
               │
        Copilot CLI ランタイム
```

**原則: ビジネスロジックはすべて Rust 側に置く。**
フロントエンドは表示と入力に徹し、判断を持たないこと。

### 4.2 Tauri コマンド（フロント → Rust）

| コマンド | 引数 | 戻り値 | 用途 |
|---|---|---|---|
| `list_agents` | なし | `Vec<AgentSummary>` | エージェント一覧の取得 |
| `get_agent_config` | `agent_id` | `AgentConfig` | 入出力設定の取得 |
| `save_agent_config` | `AgentConfig` | `()` | 入出力設定の保存 |
| `start_task` | `agent_id`, `prompt` | `SessionId` | タスクの実行開始 |
| `cancel_task` | `session_id` | `()` | 実行の中断 |
| `respond_permission` | `request_id`, `decision` | `()` | 承認ダイアログの応答 |
| `list_history` | `limit` | `Vec<HistoryEntry>` | 実行履歴の取得 |
| `open_output_folder` | `agent_id` | `()` | 出力先をエクスプローラで開く |

### 4.3 イベント（Rust → フロント）

Copilot SDK から受け取ったセッションイベントを、アプリ独自の型に**変換してから**
`emit` してください。SDK の型をそのままフロントに流さないこと（SDK 更新時の影響を
Rust 側で吸収するため）。

emit するイベント名は `agent://event` の単一チャネルとし、`kind` で判別します。

```rust
enum AppEvent {
    TaskStarted   { session_id, agent_id, started_at },
    AgentIntent   { session_id, agent_id: Option<String>, text },
    SubagentStarted   { session_id, agent_id, display_name },
    SubagentCompleted { session_id, agent_id, duration_ms, total_tokens },
    SubagentFailed    { session_id, agent_id, error },
    ToolStarted   { session_id, agent_id: Option<String>, tool_name },
    ToolCompleted { session_id, agent_id: Option<String>, tool_name, success },
    PermissionRequested { session_id, request_id, kind, detail },
    UsageUpdated  { session_id, current_tokens, token_limit },
    TaskCompleted { session_id, summary, output_files },
    TaskFailed    { session_id, error },
}
```

### 4.4 メイン／サブエージェントの判別

**これがツリー表示の要です。**

セッションイベントのエンベロープには `agent_id` フィールドがあり、
**サブエージェント由来のイベントにのみ付与され、メインエージェントと
セッションレベルのイベントには付きません。**

したがって:

- `agent_id` が `None` → メインエージェントの行に表示
- `agent_id` が `Some(id)` → その ID のサブエージェント行に表示

`subagent.started` でサブエージェント行を生成し、`subagent.completed` /
`subagent.failed` で確定させます。

## 5. データモデル

### 5.1 ファイル配置

```
<exe と同じ階層>/
├─ agent-deck.exe
└─ data/
   ├─ config.json          アプリ全体の設定
   ├─ agents.json          エージェントごとの入出力設定
   ├─ history.jsonl        実行履歴（追記のみ）
   └─ logs/                実行ログ（セッション単位）
```

ポータブル運用のため、**ユーザープロファイル配下ではなく exe と同階層**に置きます。
書き込み不可の場所（Program Files 等）に置かれた場合は、起動時にエラーを出して
別の場所への配置を促してください。

エージェント定義（`.agent.md`）は Copilot CLI の規約に従った場所に置き、
その探索パスを `config.json` で指定します。

### 5.2 `config.json`

```json
{
  "version": 1,
  "agentDirs": [
    "C:/work/agent-console/agents"
  ],
  "copilotCliPath": null,
  "defaultModel": null,
  "logLevel": "info"
}
```

`copilotCliPath` が `null` の場合は `COPILOT_CLI_PATH` 環境変数、
それも無ければ PATH から解決します。

### 5.3 `agents.json`

エージェント定義そのものではなく、**アプリ側で持つ運用設定**です。
`.agent.md` は Copilot CLI の管轄なので、アプリが勝手に書き換えないこと。

```json
{
  "version": 1,
  "agents": {
    "survey-analyst": {
      "inputDir": "C:/work/data/survey/input",
      "outputDir": "C:/work/data/survey/output",
      "allowedTools": ["write", "shell(python:*)"],
      "deniedTools": ["shell(rm)"],
      "autoApproveWriteInOutputDir": true
    }
  }
}
```

### 5.4 `history.jsonl`

1 行 1 実行。追記のみ。

```json
{"sessionId":"...","agentId":"survey-analyst","prompt":"...","startedAt":"2026-08-12T09:00:00Z","durationMs":251000,"status":"completed","outputFiles":["report_2026Q2.md"],"totalTokens":48210,"subagents":[{"name":"data-cruncher","durationMs":120000}]}
```

## 6. 権限制御

### 6.1 基本方針

**業務データを扱うため、ここは手を抜かないでください。**

Rust SDK には `permission::approve_all` / `deny_all` / `approve_if(predicate)` という
組み合わせ可能な PermissionHandler のショートカットがあります。これを使います。

判定ロジック:

1. `deniedTools` に該当 → 無条件で拒否
2. 書き込み先が `outputDir` 配下、かつ `autoApproveWriteInOutputDir` が true → 自動承認
3. `allowedTools` に該当 → 自動承認
4. それ以外 → `PermissionRequested` を emit して UI で確認

### 6.2 作業ディレクトリ

セッションの作業ディレクトリは、そのエージェントの `inputDir` の親、
または専用のワークスペースフォルダに限定します。
**ユーザープロファイル直下や、無関係なファイルを含む親フォルダを
作業ディレクトリにしないこと。**

### 6.3 パス判定の注意

`outputDir` 配下かどうかの判定は、文字列前方一致ではなく
**正規化した絶対パス**で行ってください（`..` やシンボリックリンクによる
脱出を防ぐため）。

## 7. 画面構成

### 7.1 レイアウト

3 ペイン構成。

```
┌───────────┬──────────────────────────┬─────────────┐
│ エージェント │ 実行ビュー                  │ 詳細         │
│ 一覧       │  - プロンプト入力            │  - ログ      │
│            │  - 実行中のツリー            │  - トークン   │
│            │  - 進行状況                  │  - 出力       │
│            │                            │    ファイル   │
├───────────┼──────────────────────────┴─────────────┤
│ 設定        │ 実行履歴                                 │
└───────────┴────────────────────────────────────────┘
```

### 7.2 エージェント一覧（左ペイン）

- `.agent.md` から取得した名前・説明を表示
- 入出力フォルダが未設定のものはバッジで示す
- 選択すると実行ビューに反映

### 7.3 実行ビュー（中央ペイン）

**リアルタイム表示がこのアプリの主目的**なので、ここを最も丁寧に作ってください。

```
▼ survey-analyst                          実行中  2:31
  現在: 集計スクリプトを実行しています
  │
  ├─ 🔧 bash: python analyze.py           完了  0:12
  ├─ ▼ data-cruncher (サブ)               実行中  1:04
  │    └─ 🔧 read: survey_2026Q2.csv      完了
  └─ ○ report-writer (サブ)               待機
```

- サブエージェントは親の下にインデントして表示
- 完了したサブエージェントには所要時間とトークン数を出す
- 承認要求が発生したら、該当行の直下にダイアログを出す

### 7.4 設定画面

エージェントごとの入力フォルダ・出力フォルダ・許可ツールを設定。
フォルダはダイアログで選択できるようにする。

### 7.5 UI 方針

- 情報密度を優先する。装飾は最小限
- 状態は色だけで表現しない（アイコンとテキストを併用）
- 日本語表示。フォントサイズは 13px 以上

## 9. 受け入れ条件（v0.1）

以下がすべて満たされたら v0.1 完了とします。

1. exe を任意のフォルダに置いて起動でき、インストールを要求しない
2. エージェント一覧に、定義フォルダ内の `.agent.md` がすべて表示される
3. エージェントを選び、プロンプトを入力して実行できる
4. 実行中、メインエージェントの現在の動作がリアルタイムに表示される
5. サブエージェントが起動した場合、ツリー上に別行として現れ、完了時に所要時間が出る
6. 出力フォルダ配下への書き込みは承認なしで進む
7. 出力フォルダ外への書き込みは承認ダイアログが出て、拒否すると実行が止まる
8. 実行が完了すると、生成されたファイルの一覧が表示され、フォルダを開ける
9. アプリを再起動しても、エージェントごとの入出力設定が保持されている
10. 実行履歴に、直近の実行が記録されている

## 12. 設計上の重要な注意

最後に、この領域で失敗しやすい点をまとめます。

### 12.1 数値の集計を LLM にやらせない

アンケート集計も予算消費率も、答えが一意に決まる計算です。
LLM に CSV を読ませて直接集計させると、もっともらしいが誤った数字が出ます。
上司に提出する報告書でこれをやると、信頼を一度で失います。

正しい分担:

1. エージェントに**集計スクリプトを書かせて実行させる** — 数字はスクリプトが出す
2. その出力を根拠に、**エージェントがレポートの文章を書く**
3. スクリプトは再利用できるよう保存する

この方針は `.agent.md` の Instructions に明記します。アプリ側では、
生成されたスクリプトが出力フォルダに残ることを保証してください。

### 12.2 バージョンの追跡可能性

「同じ依頼をしたのに人によって結果が違う」という相談は必ず来ます。
成果物には、使用したエージェント定義のバージョンとモデル名を
フッターに記録するようにしてください。

### 12.3 失敗時の状態

タスクが途中で失敗したとき、出力フォルダに中途半端なファイルが残ります。
「このファイルは完成品か、途中で止まったものか」が UI から判別できるように
してください（履歴の status と紐づける）。

## 付録 A: 事前確認の結果（2026-08-12 追記）

§0.1 の指示に基づく確認を実施した。詳細と出典は [docs/sdk-notes.md](docs/sdk-notes.md)。

### A.1 本仕様書の記述と食い違った点

| 該当箇所 | 仕様書の記述 | 確認された実態 |
|---|---|---|
| §5.2 | CLI が見つからなければ「PATH から解決」 | SDK は PATH スキャンをしない（README 明記）。PATH 探索は**アプリ側で実装**して明示パスを SDK に渡す |
| §5.3 | `allowedTools` に `shell(python:*)` 形式 | この形式は `.agent.md` の `tools` ではなく **CLI の `--allow-tool` / `--deny-tool` フラグの記法**。アプリはこの記法をフラグ（または SDK の相当機能）へ渡す前提で保持する |
| §4.3 | `PermissionRequested { kind }` | serde の判別タグ `kind` と衝突するため、実装ではフィールド名を `permission_kind` とした |
| §2.2 | 同梱無効化でビルド軽量化 | `default-features = false` でも build.rs は CLI をダウンロードし開発機キャッシュに展開する（配布物には入らない）。**開発機で動いても配布先で動くとは限らない**点に注意 |

### A.2 正しいと確認できた点

- `agent_id` の付与規則（§4.4）: サブエージェント由来イベントのみに付く — 生成ソースの doc コメントで確認。ツリー判別は成立する
- `permission::approve_all` / `deny_all` / `approve_if`（§6.1）: 実名のまま実在。ただし UI 確認をはさむ要件には `PermissionHandler` トレイトの自前実装が本命
- SDK と CLI のバージョン対管理（§2.2）: crate 同梱の `cli-version.txt` で固定
